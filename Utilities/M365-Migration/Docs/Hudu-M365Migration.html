M365 Tenant-to-Tenant Migration Toolkit: what to run around AvePoint Fly

What this is

A set of seventeen PowerShell scripts plus a shared module that cover the parts of a Microsoft 365 tenant-to-tenant migration that AvePoint Fly does not. Fly moves content: mailboxes, archives, OneDrive, SharePoint, Teams and Microsoft 365 Groups. The toolkit does identity: it decides what every user, mailbox, group and contact will be called in the destination tenant, provisions them, licenses them, re-applies delegation, releases the vanity domain from the old tenant, and verifies the result.

Everything hangs off one artefact, the identity plan — a CSV that names every object's destination identity. The client signs it off, an operator can edit it in Excel, and every later script reads it. Nothing downstream guesses.

Source

The scripts, the templates and the full technical README are published in the public repository: https://github.com/SatiricTech/AutomationHub_Public/tree/main/Utilities/M365-Migration. Always pull the whole M365-Migration folder — the scripts import the M365Migration module beside them and will not run as single files.

When to use it

ScenarioUse the toolkit?
Tenant-to-tenant migration with AvePoint Fly doing the content Yes — this is what it was built for
Tenant-to-tenant migration with a different mover (BitTitan, ShareGate) Yes — only Export-MigrationMappingFile is tool-specific, and a new format is one registry entry
Standardising UPNs and email addresses inside one existing tenant Yes — see "In-place UPN redesign" below
Merging an acquisition into an existing tenant Yes, with care: feed the destination inventory in as reserved addresses so nothing collides with staff already there
Splitting a tenant (divestiture) Partly — the identity and provisioning phases apply; who stays is a manual scoping decision
On-premises Exchange to Microsoft 365 No — directory-synced objects are read-only for UPN and proxy addresses in the cloud, and the toolkit stops on them by design

Where the scripts live

Repository folder: AutomationHub_Public / Utilities / M365-Migration. It holds the seventeen phase scripts, README.md (the full technical reference: every parameter, the plan schema, the auth matrix), M365Migration/ (the shared module — connections, logging, dry-run wrapper, plan reader/writer, naming engine, collision resolver), Templates/ (IdentityPlan.sample.csv, SkuMap.sample.csv, ExclusionRules.sample.csv) and Tests/ (Pester suites — run them after any change, before using the toolkit on a client).

GDAP

Check the tenant before every writer

Connect-ExchangeOnline without -DelegatedOrganization connects to our tenant, not the customer's. At best every mailbox lookup fails with "No mailbox found"; at worst a cleanup script runs against the wrong estate. Every script in the toolkit prints the tenant id and display name it actually connected to — read that line before you let anything write.

Remove-MigrationDomainReferences is the dangerous one: it is the only script that targets the tenant being left behind, and it refuses to change anything without -AcknowledgeSourceTenant on the command line.

ServiceDelegated (GDAP) parameterNotes
Microsoft Graph-TenantId <customer>.onmicrosoft.com Works for a partner user under an active GDAP relationship, scoped to the roles GDAP granted
Exchange Online-DelegatedOrganization <customer>.onmicrosoft.com Interactive/delegated only. It cannot be combined with app-only certificate auth — cross-tenant app-only EXO needs a multitenant app with per-customer consent and -Organization instead. If a delegated session lands in the wrong tenant, add -DisableWAM: WAM is known to drop GDAP claims
Microsoft Teams-TenantId <customer>.onmicrosoft.comStandard delegated sign-in

The migration runbook

Steps run in order. Every script accepts -DryRun, which connects read-only, computes the whole run, writes a results file with status Planned and changes nothing. Dry-run every writer before the real run. Output lands in %LOCALAPPDATA%\Migration-Automations\<Prefix>\ with a timestamped log per run; use -Prefix to name the client.

  1. Inventory the source tenant.

    .\Get-MigrationInventory.ps1 -Prefix Source -DelegatedOrganization contoso.onmicrosoft.com -IncludeAuthMethods

    Check: nine CSVs written and the Summary counts match the admin center. Note the MFA registration counts — everyone re-registers in the new tenant, so they drive the user comms.

  2. Inventory the destination tenant.

    .\Get-MigrationInventory.ps1 -Prefix Destination -DelegatedOrganization newco.onmicrosoft.com

    Check: any users already there — those addresses become reserved in the next step so nothing is planned on top of them.

  3. Build the identity plan. Offline — no tenant connection.

    .\New-MigrationIdentityPlan.ps1 -UsersCsv .\Source_Users_*.csv -UserMailboxesCsv .\Source_UserMailboxes_*.csv -SharedMailboxesCsv .\Source_SharedMailboxes_*.csv -GroupsCsv .\Source_Groups_*.csv -ContactsCsv .\Source_Contacts_*.csv -TargetDomain newco.com -InterimDomain newco.onmicrosoft.com -UpnFormat First.Last -SkuMapPath .\SkuMap.csv -ExclusionRulesPath .\ExclusionRules.csv -ReservedAddressesPath .\Destination_Users_*.csv -Prefix Contoso

    Check: zero Invalid rows; every NeedsReview and Collision row resolved by hand and marked ManualOverride; every Excluded row has an ExcludeReason you agree with. Send the plan to the client for sign-off — this is the artefact they approve.

  4. Export the Fly mapping file.

    .\Export-MigrationMappingFile.ps1 -PlanPath .\Contoso_IdentityPlan_*.csv -Tool AvePoint -UseInterim -Prefix Contoso

    Check: the results file shows no unexpected Skipped rows. A mapping file quietly four rows short is how mailboxes get left behind.

  5. Readiness — stage Pre.

    .\Test-MigrationReadiness.ps1 -PlanPath .\Contoso_IdentityPlan_*.csv -Stage Pre -TenantId newco.onmicrosoft.com -DelegatedOrganization newco.onmicrosoft.com -Prefix Contoso

    Check: exit code 0. It verifies domains, seats, usage locations, and whether any target address already belongs to something in the destination — including a soft-deleted user, which holds its UPN and returns 409 on create until purged or restored. Do not provision until this is clean.

  6. Fly console: create the migration project and connect both tenants. Authorise the service account in each tenant, upload the mapping file from step 4, and let Fly's own readiness check run.

    Check: Fly reports both tenants connected and the mapping accepted, with no unmatched rows.

  7. Provision the destination users.

    .\New-MigrationUsers.ps1 -PlanPath .\Contoso_IdentityPlan_*.csv -Wave 1 -UseInterim -HideFromAddressLists -SetManagers -Prefix Contoso -DryRun then again without -DryRun.

    Check: every row Succeeded and the plan now carries TargetObjectId. Generated passwords are in the results CSV and nowhere else — move that file somewhere safe immediately.

  8. Licence them.

    .\Set-MigrationLicenses.ps1 -PlanPath .\Contoso_IdentityPlan_*.csv -Wave 1 -DefaultUsageLocation US -Prefix Contoso

    Check: the seat pre-check table shows no shortfall. Any SKU that arrived through group-based licensing is skipped and reported — fix those by changing group membership, not with this script.

  9. Create mail recipients.

    .\New-MigrationRecipients.ps1 -PlanPath .\Contoso_IdentityPlan_*.csv -Wave 1 -Mode CreateAndUpdate -GroupsCsv .\Source_Groups_*.csv -ContactsCsv .\Source_Contacts_*.csv -SharedMailboxesCsv .\Source_SharedMailboxes_*.csv -DelegatedOrganization newco.onmicrosoft.com -Prefix Contoso

    Check: members and owners the plan could not map — usually ex-employees, reported per row rather than treated as fatal. Use -Mode UpdateSettings alone to patch moderation and delivery restrictions onto groups Fly already created.

  10. Readiness — stage Provisioned.

    .\Test-MigrationReadiness.ps1 -PlanPath .\Contoso_IdentityPlan_*.csv -Stage Provisioned -SourceMailboxesCsv .\Source_UserMailboxes_*.csv -TenantId newco.onmicrosoft.com -DelegatedOrganization newco.onmicrosoft.com -Prefix Contoso

    Check: every user has a mailbox, archives on where the source had one, litigation holds off, OneDrive provisioned, quota at least the source mailbox size. Writes MailboxProvisioned and OneDriveProvisioned back to the plan.

  11. Fly console: run the pre-cutover content jobs. Mailboxes, archives, OneDrive, SharePoint, Teams and Microsoft 365 Groups. Run them, then re-run deltas until each pass finishes quickly.

    Check: delta passes small, error counts stable rather than growing. Investigate recurring per-item failures before cutover, not after.

  12. Release the vanity domain in the source tenant. Report first, always.

    .\Remove-MigrationDomainReferences.ps1 -Domain contoso.com -ReportOnly -TenantId contoso.onmicrosoft.com -DelegatedOrganization contoso.onmicrosoft.com -Prefix Contoso

    Then, with the acknowledgement:

    .\Remove-MigrationDomainReferences.ps1 -Domain contoso.com -AcknowledgeSourceTenant -TenantId contoso.onmicrosoft.com -DelegatedOrganization contoso.onmicrosoft.com -Prefix Contoso

    Check: exit code 0 and an empty Blockers CSV. Then remove the domain from the source tenant and verify it in the destination.

  13. Cutover day: mail flow. Change MX to the destination tenant, update SPF, DKIM and DMARC, and repoint or rebuild any connectors and third-party mail filter.

    Check: send a test message in and out. Confirm the destination is receiving before you touch identities.

  14. Apply the target identities.

    .\Set-MigrationIdentity.ps1 -PlanPath .\Contoso_IdentityPlan_*.csv -Wave 1 -Apply Upn,PrimarySmtp,Aliases,X500,MailNickname,GalVisibility -Unhide -MatchOn TargetObjectId -DisableEmailAddressPolicy -TenantId newco.onmicrosoft.com -DelegatedOrganization newco.onmicrosoft.com -Prefix Contoso

    Check: spot-check three users — UPN, primary SMTP, aliases, X500, no longer hidden. Directory-synced rows report Failed; that is correct, and they have to be fixed on-premises.

  15. Re-apply mailbox delegation.

    .\Set-MigrationMailboxPermissions.ps1 -PlanPath .\Contoso_IdentityPlan_*.csv -MailboxPermissionsCsv .\Source_MailboxPermissions_*.csv -UserMailboxesCsv .\Source_UserMailboxes_*.csv -SharedMailboxesCsv .\Source_SharedMailboxes_*.csv -Apply FullAccess,SendAs,SendOnBehalf,Calendar,Forwarding -Wave 1 -Prefix Contoso

    Check: the Skipped rows — an unmapped trustee is a person who will phone the service desk. Re-running is safe; existing permissions are reported as already present.

  16. Reset cutover passwords.

    .\Reset-MigrationCutoverPasswords.ps1 -PlanPath .\Contoso_IdentityPlan_*.csv -Wave 1 -Prefix Contoso

    Check: one passphrase per user in the results CSV, every account flagged to change password at next sign-in. Distribute out of band — never by email to the tenant being migrated.

  17. Teams Phone. Release the numbers in the source, then reassign them in the destination once the port completes. Port lead time gates the cutover date; start it weeks ahead.

    .\Get-MigrationTeamsPhoneAssignments.ps1 -Prefix Source -TenantId contoso.onmicrosoft.com -IncludeUnassignedNumbers

    .\Remove-MigrationTeamsPhoneAssignments.ps1 -CsvPath .\Source_TeamsPhoneAssignments_*.csv -TenantId contoso.onmicrosoft.com

    .\Set-MigrationTeamsPhoneAssignments.ps1 -CsvPath .\Source_TeamsPhoneAssignments_*.csv -TenantId newco.onmicrosoft.com

    Check: run -ListUnassigned against the destination first to confirm the numbers arrived. Users need a Teams Phone licence already. Hybrid numbers synced from on-premises AD cannot be released by script and report Failed.

  18. Viva Learning history (optional).

    .\Get-MigrationVivaLearningHistory.ps1 -Prefix Source -TenantId contoso.onmicrosoft.com, then .\Import-MigrationVivaLearningHistory.ps1 -CsvPath .\Source_VivaLearningHistory_*.csv -TenantId <destination-tenant-id> -ClientId <app-id> -PlanPath .\Contoso_IdentityPlan_*.csv -Prefix Contoso -DryRun

    Check: fill in blank CourseTitle and CourseWebUrl cells (built-in provider rows export empty) before the real import. Catalog content can take 24 hours to appear in search.

  19. Readiness — stage Post.

    .\Test-MigrationReadiness.ps1 -PlanPath .\Contoso_IdentityPlan_*.csv -Stage Post -TenantId newco.onmicrosoft.com -DelegatedOrganization newco.onmicrosoft.com -Prefix Contoso

    Check: exit code 0. UPN, primary SMTP, every alias, X500, unhidden, enabled.

  20. Compare. Re-inventory the destination and diff it against the plan.

    .\Get-MigrationInventory.ps1 -Prefix Post -DelegatedOrganization newco.onmicrosoft.com, then .\Compare-MigrationUserData.ps1 -PlanPath .\Contoso_IdentityPlan_*.csv -DifferenceCsv .\Post_Users_*.csv -Prefix Contoso

    Check: every plan row matched. Anything unmatched is a person or mailbox that did not make it — cheaper to find now than in a week.

Identity plan and UPN design decisions

The plan is built once, reviewed by a human, and read by everything after it. Make these decisions deliberately before generating it.

Choosing the format

-UpnFormat takes a preset or a raw template. Presets: First.Last (the default), FLast, F.Last, FirstLast, First, First.L, FirstL, First.M.Last, FMLast, Last.First, Keep. Templates use the tokens {first} {last} {middle} {f} {m} {l} {source} {display} with truncation as {last:5}, so an unusual house style is one string, not a code change.

SituationChoice
Client has a house standard alreadyMatch it. Consistency across the estate beats elegance
Source tenant is firstname-only (john@) and the client wants first.last -UpnFormat First.Last. The templates build from the inventory's FirstName and LastName columns, not from the old address — nothing carries over
Large organisation, many shared surnamesFirst.M.Last or First.Last with middle-initial collision handling — cleaner than numeric suffixes
Existing addresses must survive verbatim-UpnFormat Keep, which reuses the source local part

Names are transliterated before templating: accents stripped, apostrophes and spaces removed, hyphens kept — O'Brien → obrien, van der Berg → vanderberg, Smith-Jones → smith-jones.

Collisions

Two people templating to the same address are resolved deterministically: the first by source object id keeps it, the next tries the middle-initial form, and only then does a numeric suffix appear. Every changed row is flagged Collision, and writers ignore those unless you pass -IncludeCollisions — a suffix is always somebody's decision, never something that happened quietly. Ordering is by object id, so re-running the planner after an edit never reshuffles names already provisioned. A name the template cannot complete — no surname, a non-Latin script — comes out NeedsReview with empty target columns. The tool does not guess.

Interim domain

The vanity domain can only live in one tenant at a time

The destination cannot verify contoso.com until the source releases it, and the source cannot release it until every object there has moved off it. So users are provisioned on newco.onmicrosoft.com first and switched at cutover. The plan carries both Interim* and Target* columns: provision with -UseInterim, then apply Target* with Set-MigrationIdentity once the domain has moved. Omit -InterimDomain only when the domain is already in the destination, or for an in-place redesign.

UPN is not the email address

-SmtpFormat defaults to the UPN format, so usually they match. Setting it separately gives a user who signs in as jsmith@newco.onmicrosoft.com and receives mail as john.smith@newco.com. Those rows are flagged UpnSmtpDiverge deliberately — the service desk needs to know who signs in with an address that is not their email, or it is a guaranteed ticket. Make it a conscious choice and put it in the user comms.

In-place UPN redesign

The same tooling standardises addressing inside one tenant with no migration at all: inventory the tenant, run the planner against its own export with the tenant's own domain as -TargetDomain and no interim domain, review the plan, then apply with Set-MigrationIdentity -MatchOn Source. Matching on the source address is the trick — the objects already exist, so Source* describes today and Target* the new scheme. The old primary is kept as an alias unless you pass -RemoveOldPrimaryAlias.

Troubleshooting

SymptomCauseFix
Replies to pre-migration mail bounce with an IMCEAEX non-delivery report The source LegacyExchangeDN was never stamped on the destination object as an X500 address Set-MigrationIdentity -Apply X500. The plan already carries the DN from the source inventory
Primary SMTP reverts to the old address a day later An email address policy re-asserted it Re-run with -DisableEmailAddressPolicy, which turns off EmailAddressPolicyEnabled before the address write
Address changed in Entra but mail still routes to the old address Graph's mail property is cosmetic on a mailbox-enabled user; Exchange owns proxyAddresses Use the toolkit, which always writes primary SMTP through Set-Mailbox -EmailAddresses, never Graph
assignLicense fails, or the admin center shows "invalid usage location" The user has no usage location, which the licence call requires Set UsageLocation in the plan, or pass -DefaultUsageLocation
A licence will not come off, or comes back doubled It was assigned by a group (assignedByGroup is set), and assignLicense cannot remove those Change the group membership, or exclude the service plan on the group assignment. Set-MigrationLicenses skips and reports these rather than fighting them
User create or UPN rename returns 409 "already exists" and nothing visible holds the address A soft-deleted user still holds the UPN or a proxy address Test-MigrationReadiness -Stage Pre lists them. Purge or restore the deleted object, then re-run
403 Authorization_RequestDenied renaming or resetting one particular account The target holds an admin role; User.ReadWrite.All and User Administrator are not enough Use Privileged Authentication Administrator (or Global Admin) for that account
"Out of the current user's write scope" changing an address, or the row reports Failed as synced The object is directory-synced; Exchange Online and Entra are read-only for its UPN and proxy addresses Change it in on-premises AD and let AAD Connect sync. The toolkit stops rather than pretending it worked
A user is still visible in the GAL despite -HideFromAddressLists Graph's showInAddressList is a documented known issue and Exchange's own setting wins once a mailbox exists Re-apply after licensing with Set-MigrationIdentity -Apply GalVisibility
Fly refuses a mailbox Litigation hold is on, or the destination mailbox has not been provisioned Test-MigrationReadiness -Stage Provisioned reports both. Clear the hold for the move window and confirm the mailbox exists
Fly cannot write to a user's OneDrive OneDrive is not provisioned — GET /users/{id}/drive returns 404 until it is Pre-provision with Request-SPOPersonalSite -UserEmails <email> (SharePoint Admin, user already licensed), then re-check readiness
Fly jobs fail to authenticate part-way through The service account hit MFA or a Conditional Access policy Exclude it from MFA and CA in both tenants for the project, and re-enable when it closes
The domain will not delete from the source tenant Something still references it: a user UPN, a proxy address, a group, a mailbox or a contact Remove-MigrationDomainReferences -ReportOnly lists every one plus the blockers it cannot fix. Guest #EXT# UPNs are informational, not blockers. The initial .onmicrosoft.com domain can never be removed
EXO connects to our tenant instead of the customer's under GDAP Missing -DelegatedOrganization, or WAM dropped the GDAP claims Pass -DelegatedOrganization <customer>.onmicrosoft.com, and add -DisableWAM if it still lands wrong
Tenant-wide permission export dies with "data exceeded max permitted by session (500MB)" Remote-PowerShell Get-MailboxPermission on a large estate The inventory already uses the REST-based Get-EXOMailboxPermission. On very large tenants add -SkipMailboxPermissions and batch them
A Teams number will not release from the source tenant It is a hybrid number synced from on-premises AD (OnPremLineURI) Clear it on-premises. The script reports these as Failed rather than silently skipping
Viva Learning rows fail with a licensing 403 The target learner has no Viva Learning premium licence Licence them and re-run — the import is idempotent and skips activities that already exist

Known Fly limitations — set client expectations early

Agree these in writing before the project starts

Every one of these has caused a post-migration complaint on somebody's project. They are cheap to explain up front and expensive to explain afterwards.

AreaLimitation
Teams chatsMode-dependent and lossy: no reactions, no external or federated chats, authorship rendered rather than reproduced. Agree the chat mode with the client and show a sample before the full run
Microsoft 365 Groups and PlannerConversation comments are lost and Planner task dates shift
Distribution listsMembers and owners only — moderation, delivery restrictions and send-on-behalf do not come across. New-MigrationRecipients re-applies them from the inventory
Entra moduleCreates users and security groups, but with no password, no manager and sign-in blocked. It does not create distribution lists, mail-enabled security groups or contacts at all
LicensingFly's auto-licensing only works when there are both spare seats and a usage location already set. Run Set-MigrationLicenses first rather than relying on it
GuestsNot migrated as objects — they have to be re-invited, and every guest re-accepts
MFA and devicesNothing authentication-related moves. Every user re-registers MFA and every managed device re-enrols
Mail flowMX, connectors and any third-party filter are entirely manual
Compliance dataeDiscovery holds, retention policies, audit history and Purview configuration do not migrate
Other workloadsBookings, Shifts, Power Platform (optional module), Stream and Viva Learning are out of scope or partial — Viva Learning has its own scripts here
Exchange Web ServicesEWS retires on 1 October 2026. Confirm Fly is running its Graph-based path before scheduling a cutover anywhere near that date
