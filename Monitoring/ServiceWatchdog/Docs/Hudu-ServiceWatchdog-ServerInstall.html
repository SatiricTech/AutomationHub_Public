What this page is for

Follow it to register one Windows server with the service watchdog. Once registered, the server restarts any listed Windows service that stops and emails IT when it cannot. Nothing here touches the Azure side; that is already deployed. Registering another server means repeating these steps on that server.

Values you need before you start

ItemValueNotes
Function URL[FUNCTION URL]Goes in Webhook.Url. Same for every server.
Function key[FUNCTION KEY OR VAULT ENTRY]Goes in Webhook.FunctionKey. Treat it like a password: never email it, never paste it into a ticket.
Site name[SITE NAME]Goes in SiteName; appears in the subject line of every alert.
Install files[WHERE THE ENDPOINT FOLDER IS KEPT]The Endpoint folder: three scripts and an example config.
Who to ask[CONTACT]For the values above, or if a step fails.

Requirements

  • Windows Server 2016 or later. Windows PowerShell 5.1, which is built in, is enough.
  • A local Administrator account; every command below runs in an elevated PowerShell.
  • Outbound HTTPS (TCP 443) from the server to the function URL.
  • The names of the Windows services to watch (see the service-name rule in step 3).

Step 1: copy the files

Copy the Endpoint folder to any temporary location on the server, for example C:\Temp\Endpoint.

The installer does not install where you run it from

The folder you copied is only the source. The installer creates and uses C:\ProgramData\ServiceWatchdog for the config file, the state file, the logs and its own copy of the worker script. The file you edit in step 3 is C:\ProgramData\ServiceWatchdog\ServiceWatchdog.json; it will not appear next to the scripts you ran. You can delete the temporary folder after step 5.

Step 2: first run of the installer

cd C:\Temp\Endpoint
.\Register-WinServiceWatchdogTask.ps1

Expected result: one line ending in Edit it (Services, Webhook.Url, Webhook.FunctionKey) and re-run this script, and exit code 2. That is success for the first run: the install folder now exists, is locked down to SYSTEM and Administrators, and holds a config file for you to fill in.

Step 3: edit the config file

Open C:\ProgramData\ServiceWatchdog\ServiceWatchdog.json in Notepad (as administrator) and set these four values. Leave everything else at its default unless [CONTACT] says otherwise.

{
  "SchemaVersion": 1,
  "SiteName": "[SITE NAME]",
  "Services": [ "Spooler", "W3SVC", "MSSQLSERVER" ],
  "Webhook": {
    "Url": "[FUNCTION URL]",
    "FunctionKey": "[FUNCTION KEY]"
  }
}
Use the service Name, not the Display Name

Windows services have two names. The watchdog wants the short Name, which is what the logs, the emails and Windows itself key on. The friendly Display Name is what the Services console shows in its first column.

Use this (Name)Not this (Display Name)
SpoolerPrint Spooler
W3SVCWorld Wide Web Publishing Service
MSSQLSERVERSQL Server (MSSQLSERVER)

To look a name up, run Get-Service | Sort-Object DisplayName | Select-Object Name, DisplayName, or for one service (Get-Service -DisplayName 'Print Spooler').Name. In the Services console the Name is on the General tab of a service's properties, labelled "Service name".

Any value still containing REPLACE is rejected. Use straight double quotes and a comma between list items, as in the example.

Step 4: register the task and send a test

cd C:\Temp\Endpoint
.\Register-WinServiceWatchdogTask.ps1 -TestAlert -RunNow

Expected result: a summary ending with the task name, the next run time and the log path, exit code 0, and within a minute an email with [TEST] in the subject in the IT mailbox. From now on the server checks its services every 5 minutes and 5 minutes after every reboot, as the SYSTEM account.

Optional: add -SetServiceRecovery to the command to also have Windows restart each listed service on its own if it crashes.

Step 5: confirm it is running

Get-ScheduledTask -TaskName ServiceWatchdog | Get-ScheduledTaskInfo
Get-WinEvent -FilterHashtable @{ LogName = 'Application'; ProviderName = 'ServiceWatchdog' } -MaxEvents 5

LastTaskResult of 0 and a recent LastRunTime mean the task ran. Event 1030 is the test alert; event 1000 or 1001 means a normal run. The daily log file is in C:\ProgramData\ServiceWatchdog\Logs.

Running a check right away

You do not have to wait for the next 5-minute run:

Start-ScheduledTask -TaskName ServiceWatchdog

That runs the same check the schedule would, as SYSTEM; read the outcome from the event log command above or the daily log file. To watch a run on screen instead, run the worker from the install folder; add -DryRun to only see what it would do without starting services or sending mail:

cd C:\ProgramData\ServiceWatchdog
.\Invoke-WinServiceWatchdog.ps1 -Verbosity High

Changing the service list later

Edit the JSON file, then check it from the install folder. No re-registration is needed; the next scheduled run picks the change up.

cd C:\ProgramData\ServiceWatchdog
.\Invoke-WinServiceWatchdog.ps1 -ValidateConfig

Removing the watchdog from a server

cd C:\Temp\Endpoint
.\Unregister-WinServiceWatchdogTask.ps1 -RemoveEventSource -RemoveFiles -Force

Tell [CONTACT] afterwards so the server is removed from the daily check-in report; otherwise it is reported as silent.

If something fails

What you seeMeaningWhat to do
Installer stops at once mentioning elevation (exit 1)PowerShell is not running as administratorOpen PowerShell with "Run as administrator" and try again
Exit 2 naming a config keyThe JSON is invalid or still has a REPLACE valueFix the named key; check quotes and commas
Exit 2 saying the worker already existsThe installer was already run on this serverRe-run with -Force added
Exit 10, or event 1013 in the Application logThe function rejected the keyCheck Webhook.FunctionKey for a copy error; ask [CONTACT] if it persists
Event 1011The server could not reach the function URLCheck outbound HTTPS and any proxy; the alert is retried automatically
Event 1003 or 1004 after registrationA listed service is not installed, or is DisabledFix the name (step 3) or remove it from the list
Do not

Do not edit the scripts, do not copy the key anywhere else, and do not change the scheduled task by hand. Everything the watchdog needs is in the JSON file.
