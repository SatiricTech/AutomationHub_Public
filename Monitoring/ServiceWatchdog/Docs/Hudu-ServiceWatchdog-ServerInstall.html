What this page is for

Follow it to register one Windows server with the service watchdog. Once registered, the server restarts any watched Windows service that stops and emails IT when it cannot. Nothing here touches the Azure side; that is already deployed. Registering another server means repeating these steps on that server.

There are two ways to do it. Option A, the drop-and-deploy package, is the default: copy a folder, double-click one file, tick services, press a button. Option B is the manual PowerShell path, for servers without a desktop session or when you are scripting the install.

Source

The scripts, the deployment template and the full technical documentation are published in the public repository: https://github.com/SatiricTech/AutomationHub_Public/tree/main/Monitoring/ServiceWatchdog. The package for Option A is built from there for each deployment and carries a pinned copy of the Endpoint scripts; for Option B, take the Endpoint folder from the repository so servers get the current version.

Requirements

  • Windows Server 2016 or later. Windows PowerShell 5.1, which is built in, is enough.
  • A local Administrator account. Option A asks for elevation (UAC) itself; Option B runs in an elevated PowerShell.
  • Outbound HTTPS (TCP 443) from the server to the function URL. If the server uses a proxy, it must be the machine-wide WinHTTP proxy.
The installer does not install where you run it from

Whatever folder you copy to the server is only the source. The installer creates and uses C:\ProgramData\ServiceWatchdog for the config file, the state file, the logs and its own copy of the worker script, locked down to SYSTEM and Administrators. The scheduled task runs from there.

Which services to watch

The ones a user would notice within minutes if they stopped: the line-of-business application service, SQL Server, IIS, the print spooler on a print server. Do not pick services that are meant to stop on their own (manual-start helpers, update services), or the watchdog will keep restarting them and emailing about it. When in doubt, ask [CONTACT].

Option A: drop-and-deploy package (default)

A1: copy the folder

Copy the whole ServiceWatchdog package folder to the server, for example to C:\Temp\ServiceWatchdog. Any location works, including one with spaces in the path. It contains Run-ServiceWatchdog.cmd, Install-WinServiceWatchdogGui.ps1, ServiceWatchdog.settings.json, PACKAGE-VERSION.txt and an Endpoint folder. Keep it together; do not copy files out of it.

A2: double-click Run-ServiceWatchdog.cmd

Accept the UAC prompt. The launcher runs the window in Windows PowerShell (never PowerShell 7) in the mode WinForms needs. A window titled ServiceWatchdog – [client name] opens. From top to bottom it shows:

  • Site name box (appears in the alert emails; up to 64 characters), the Filter services box and a count of ticked services.
  • The service list, each shown as Display Name (ShortName) [Status], running services first, then the rest alphabetically.
  • The buttons Install, Send test alert, Check status and Uninstall.
  • A Logs drop-down with a View logs button.
  • A read-only log pane that streams the underlying scripts' output (the function key is never shown), and a status bar with the task's state, last run and last result.

If a message box appears and the window closes instead, it names the problem; see If something fails.

A3: check the site name and tick the services

The site name is pre-filled with the computer name (or, on a server that already has the watchdog, the installed site name). Leave it unless a friendlier name is wanted. Tick every service the server must keep running; type in the filter box to narrow the list by either the short name or the display name. You do not need to know short names; the window writes them for you. At least one service must be ticked.

A4: press Install, then Send test alert

Press Install. The controls grey out and the log pane fills while the installer works; allow one to three minutes. It writes the config, locks down the install folder, copies the worker, validates everything, registers the scheduled task and runs it once. Expected result: a message box saying the install succeeded and that no test email was sent. From now on the server checks its services every 5 minutes and 5 minutes after every reboot, as the SYSTEM account.

Then press Send test alert. Within a minute an email with [TEST] in the subject should reach the IT mailbox. If it does not, the task is still registered and working; the problem is on the email path. Use View logs and see If something fails.

A5: confirm it is running

Press Check status. It shows whether the task exists, its last run and result, whether the installed config still validates, and the last 20 lines of today's log. A last result of 0 - Healthy, or every stopped service was restarted with a recent run time means the task ran. 267011 - the task has not run yet right after Install is normal; press it again a minute later.

A6: delete the copied folder

The task runs from C:\ProgramData\ServiceWatchdog, so the copied folder is no longer needed. Delete it. It holds the function key, and wherever it was copied it keeps that folder's ordinary permissions, which usually let any local user read it. Ask [CONTACT] for the package again when a service needs adding or removing.

Adding or removing a service later

Copy the package back to the server, double-click Run-ServiceWatchdog.cmd, change the ticks (the current site name and services are pre-filled) and press Install. That rewrites the config and re-registers the task. Delete the folder again afterwards.

Install rewrites the whole config

On a server set up with the package, make every change through the window. Hand edits to ServiceWatchdog.json are overwritten by the next Install. If the function key has been rotated, use a freshly built package: an old one still holds the old key and would put it back.

Option B: manual PowerShell install

B1: copy the files

Copy the repository's Monitoring/ServiceWatchdog/Endpoint folder to any temporary location on the server, for example C:\Temp\Endpoint. The file you edit in B3 is C:\ProgramData\ServiceWatchdog\ServiceWatchdog.json; it will not appear next to the scripts you ran. You can delete the temporary folder after B4.

B2: first run of the installer

cd C:\Temp\Endpoint
.\Register-WinServiceWatchdogTask.ps1

Expected result: one line ending in Edit it (Services, Webhook.Url, Webhook.FunctionKey) and re-run this script, and exit code 2. That is success for the first run: the install folder now exists, is locked down to SYSTEM and Administrators, and holds a config file for you to fill in.

One-pass alternative: put a filled-in ServiceWatchdog.json next to the script in C:\Temp\Endpoint first. The first run then seeds the install folder from it and goes straight on to validation and registration (add -TestAlert -RunNow). Delete that source copy afterwards; it holds the key.

B3: edit the config file

Open C:\ProgramData\ServiceWatchdog\ServiceWatchdog.json in Notepad (as administrator) and set these four values. Leave everything else at its default unless [CONTACT] says otherwise.

{
  "SchemaVersion": 1,
  "SiteName": "[SITE NAME]",
  "Services": [ "Spooler", "W3SVC", "MSSQLSERVER" ],
  "Webhook": {
    "Url": "[FUNCTION URL]",
    "FunctionKey": "[FUNCTION KEY]"
  }
}
Use the service Name, not the Display Name

Windows services have two names. The watchdog wants the short Name, which is what the logs, the emails and Windows itself key on. The friendly Display Name is what the Services console shows in its first column.

Use this (Name)Not this (Display Name)
SpoolerPrint Spooler
W3SVCWorld Wide Web Publishing Service
MSSQLSERVERSQL Server (MSSQLSERVER)

To look a name up, or for one service by its display name:

Get-Service | Sort-Object DisplayName | Select-Object Name, DisplayName
(Get-Service -DisplayName 'Print Spooler').Name

Any value still containing REPLACE is rejected. Use straight double quotes and a comma between list items, as in the example.

B4: register the task and send a test

cd C:\Temp\Endpoint
.\Register-WinServiceWatchdogTask.ps1 -TestAlert -RunNow

Expected result: a summary ending with the task name, the next run time and the log path, exit code 0, and within a minute an email with [TEST] in the subject in the IT mailbox.

Optional: add -SetServiceRecovery to also have Windows restart each listed service on its own if it crashes (restart after 1 and 2 minutes). Every re-run after the first install needs -Force.

B5: confirm it is running

Get-ScheduledTask -TaskName ServiceWatchdog | Get-ScheduledTaskInfo
Get-WinEvent -FilterHashtable @{ LogName = 'Application'; ProviderName = 'ServiceWatchdog' } -MaxEvents 5

LastTaskResult of 0 and a recent LastRunTime mean the task ran. Event 1030 is the test alert; event 1000 or 1001 means a normal run. The daily log file is in C:\ProgramData\ServiceWatchdog\Logs.

Changing the service list later (Option B servers)

Edit the JSON file, then check it from the install folder. No re-registration is needed; the next scheduled run picks the change up.

cd C:\ProgramData\ServiceWatchdog
.\Invoke-WinServiceWatchdog.ps1 -ValidateConfig

Either option

Running a check right away

You do not have to wait for the next 5-minute run:

Start-ScheduledTask -TaskName ServiceWatchdog

To watch a run on screen instead, run the worker from the install folder in an elevated PowerShell; add -DryRun to only see what it would do without starting services or sending mail:

cd C:\ProgramData\ServiceWatchdog
.\Invoke-WinServiceWatchdog.ps1 -Verbosity High

Checkup: has it restarted anything?

A successful restart is silent by default (no email), so this is the quickest way to see the watchdog doing its job. Event 1001 is written every time it starts a service:

Get-WinEvent -FilterHashtable @{ LogName = 'Application'; ProviderName = 'ServiceWatchdog'; Id = 1001 } -MaxEvents 25

Each entry names the service and the attempt it succeeded on. Use Id = 1002 for failed starts instead, or drop the Id filter for the last 25 events of any kind. In the window, View logs with Last 50 events (Application log) shows the same thing.

Removing the watchdog from a server

Option A: open the window and press Uninstall. That removes the task and keeps the config and logs for a later reinstall. For a complete removal, including the install folder and the config that holds the key, use the command below.

cd C:\Temp\Endpoint     # or the Endpoint folder inside the package
.\Unregister-WinServiceWatchdogTask.ps1 -RemoveEventSource -RemoveFiles -Force

Tell [CONTACT] afterwards so the server is removed from the daily check-in report; otherwise it is reported as silent.

Two logs matter when asking for help, both in C:\ProgramData\ServiceWatchdog\Logs: the window's own log Install-WinServiceWatchdogGui-<timestamp>.log and the watchdog's daily log ServiceWatchdog-<date>.log. Attach those to the ticket, never the package folder or the config.

Do not

Do not edit the scripts, do not copy the key or ServiceWatchdog.settings.json anywhere else, and do not change the scheduled task by hand.
