ServiceWatchdog: Windows service monitoring with email alerts

What this is

ServiceWatchdog keeps a named list of Windows services running on a server and emails IT when it cannot. A scheduled task runs a PowerShell worker every 5 minutes (and 5 minutes after boot) as SYSTEM. The worker starts stopped services, retries inside a time budget, and reports state changes to a small Azure Function that sends the email. A daily heartbeat lets the Azure side notice a server whose watchdog has gone silent.

The Azure side never touches services; it only relays and correlates what each server reports. Nothing on the server needs a mail account or an open SMTP port, only outbound HTTPS.

Source

The scripts, the deployment template and the full technical documentation are published in the public repository: https://github.com/SatiricTech/AutomationHub_Public/tree/main/Monitoring/ServiceWatchdog. Always take the Endpoint folder from there so servers get the current version.

How it works

ComponentWhereRole
Invoke-WinServiceWatchdog.ps1Each monitored server, C:\ProgramData\ServiceWatchdog The worker. Reads ServiceWatchdog.json, checks every listed service, starts stopped ones in up to MaxStartAttempts rounds inside MaxRunSeconds, compares with the previous run's state file, POSTs at most one event per run, writes a daily log and Application event log entries (source ServiceWatchdog).
Scheduled task ServiceWatchdogTask Scheduler root folder Runs the worker as SYSTEM every 5 minutes and 5 minutes after boot; one instance at a time; 7-minute execution limit.
SendServiceWatchdogAlertAzure Function App (PowerShell, Windows Consumption plan) HTTP endpoint (POST /api/servicewatchdog/alert, function key in the x-functions-key header). Validates the payload strictly, deduplicates on EventId, rate-limits per host, renders HTML plus plain-text email, sends it, records the host's last-seen time.
SendServiceWatchdogDigestSame Function App, timer Daily digest of servers that have not reported within 26 hours (or a "no hosts have ever reported" notice).
Key VaultAzure Holds the SMTP2GO API key (or SMTP password). The Function App reads it through a Key Vault reference with its managed identity.
Storage tables WatchdogHosts, WatchdogSentEventsAzure storage account Last-seen time per host, and one row per delivered EventId for deduplication.
SMTP2GOMail provider Sends the email through its REST API (default) or as an authenticated SMTP relay on 587 or 2525.

What triggers an email

EventWhenSubject marker
alertA service is newly Failed (could not be started after retries), Missing (not installed) or Disabled (start type Disabled; never touched)none
reminderThe problem is still present after ReminderMinutes (default 4 hours), repeated at that cadenceReminder:
recoveredA problem service is running again, whether the watchdog started it or someone else didnone
remediatedThe watchdog itself started a stopped service. Off by default (NotifyOnRemediation), so routine self-healing is silentnone
flappingFour transitions between healthy and a problem state inside 60 minutes; further mail for that service is suppressed for ReminderMinutesFlapping:
test-TestAlert on a server or -SendTestEmail at deployment[TEST]
heartbeatOnce every 24 hours per server. Never emailed; only updates the last-seen time used by the digestn/a

Every email lists every monitored service on that server (name, status, start type, attempts, first failed, last error) with an asterisk on the ones that triggered it, plus the site, host, FQDN, time, run id and event id. If the webhook is unreachable the server keeps the event pending and re-sends it on the next run with the same event id, so an outage neither loses nor duplicates an email.

Prerequisites

  • Monitored server: Windows Server 2016 or later, Windows PowerShell 5.1 (PowerShell 7 also works), local administrator rights for the one-time install, outbound HTTPS (443) to the Function App host name. If the server uses a proxy, it must be the machine-wide WinHTTP proxy; SYSTEM does not use a user's browser proxy.
  • Operator workstation (Azure deployment only): PowerShell 7.4 or later, Az modules 9.7.1 or later (Az.Accounts, Az.Resources, Az.Websites, Az.KeyVault), the Bicep CLI on PATH, and Contributor plus User Access Administrator (or Owner) on the target resource group.
  • SMTP2GO: a verified sender domain, a dedicated API key with only the Emails (/email/send) permission and a per-key rate limit. Do not enable the account-level API IP allowlist: a Consumption Function App has no fixed outbound IP.

Deploying the Azure side (once per deployment)

Do this before touching any server

The servers need the alert URL and function key that this step produces. Every step of the install script is idempotent; re-run it to change recipients or to push new function code.

  1. In SMTP2GO: verify the sender domain (three CNAME records), create the scoped API key, set its rate limit (for example 60 per hour; required, not optional: the function has its own global cap of 60 emails per hour, but the provider-side limit is the one that still holds if the function app is misused). For an SMTP relay, apply the relay's equivalent per-account limit.
  2. From the repository folder Monitoring/ServiceWatchdog/Deploy: 
    Connect-AzAccount
$apiKey = Read-Host -Prompt 'SMTP2GO API key' -AsSecureString
./Install-AzureServiceWatchdogFunction.ps1 `
    -ResourceGroupName 'rg-servicewatchdog' -Location 'eastus2' -BaseName 'svcwatchdog' `
    -MailFrom 'Service Watchdog <alerts@example.com>' -MailTo 'it@example.com;oncall@example.com' `
    -Smtp2GoApiKey $apiKey -SendTestEmail -Verbosity Medium
    The script deploys the Bicep template (Function App, Key Vault, storage tables, Application Insights, role assignments), seeds the secret, publishes the function code, restarts the app, creates a named function key (watchdog), prints the alert URL and key to the console once, and then verifies admin endpoint isolation (a failure there ends with exit 50 after the key was shown; the deployment is still usable). -SendTestEmail sends a [TEST] email to the recipients; a test event never creates a host row, so the workstation does not appear in the stale-host digest.
  3. Store the function key in [PASSWORD VAULT ENTRY] and record the alert URL in the table above. The key is never written to the log file.
  4. For an SMTP relay instead of the REST API, pass -MailProvider Smtp -SmtpHost ... -SmtpPort 587 -SmtpCredential (Get-Credential). Port 25 is blocked on most Azure subscriptions; implicit TLS on 465 is not supported.
Secrets

The function key and the SMTP2GO API key never go into a ticket, chat, this article or the log files. The function key lives only in ServiceWatchdog.json on each server (a folder restricted to SYSTEM and Administrators) and in [PASSWORD VAULT ENTRY]. The SMTP2GO key lives only in Key Vault (secret Smtp2GoApiKey) and in the SMTP2GO console. Recipients are fixed in the Function App settings; nothing a server sends can redirect mail.

Installing on a server

The installer does not install where you run it from

Wherever you copied the Endpoint folder is only the source. The installer creates and uses C:\ProgramData\ServiceWatchdog for the config file, the state file, the logs and its own copy of the worker script, unless you pass -InstallPath on every run. So after the first run, the file to edit is C:\ProgramData\ServiceWatchdog\ServiceWatchdog.json, and it will not appear next to the scripts you ran. The source folder can be deleted once the task is registered.

Use the service Name, not the Display Name

Services takes the short Name that Get-Service shows: Spooler, not Print Spooler; W3SVC, not World Wide Web Publishing Service. Look one up with (Get-Service -DisplayName 'Print Spooler').Name. A display name is resolved as a courtesy, but the short name is what the logs, emails and state file key on.

Handing registration to another team

The separate article ServiceWatchdog: registering a server covers only these steps, with fill-in fields for the URL, key and site name, and can be given to the staff who register servers without the rest of this page.

  1. Copy the repository's Monitoring/ServiceWatchdog/Endpoint folder to the server (for example C:\Temp\Endpoint).
  2. In an elevated PowerShell, run .\Register-WinServiceWatchdogTask.ps1. The first run creates C:\ProgramData\ServiceWatchdog, locks it down to SYSTEM and Administrators, copies an example config into it and stops with exit 2 asking for the config to be edited. If that folder already exists and is owned by another account, the installer refuses it (exit 2): remove the folder or take ownership first.
  3. Edit C:\ProgramData\ServiceWatchdog\ServiceWatchdog.json: set SiteName (the customer or site as it should appear in the email), Services (service short names, for example Spooler rather than Print Spooler; Get-Service | Select Name, DisplayName shows both), Webhook.Url and Webhook.FunctionKey. Any value still containing REPLACE fails validation.
  4. Run .\Register-WinServiceWatchdogTask.ps1 -TestAlert -RunNow (add -SetServiceRecovery to also set Service Control Manager failure actions, restart after 1 and 2 minutes, on every listed service). This re-applies the folder lockdown, copies the worker, validates the config, registers the event source and the task, starts it and sends a test alert.
  5. Confirm the [TEST] email arrived, then run the checks under Testing an installation.
Re-running the installer is safe

Re-run it to change the interval (-IntervalMinutes) or the execution limit; the task is always re-registered. Every re-run after the first install needs the script's own -Force, because the worker is already in place (the copy is idempotent and also serves as the upgrade path): .\Register-WinServiceWatchdogTask.ps1 -Force -IntervalMinutes 10. -DryRun shows every step without changing anything.

Editing the service list later

Edit Services in ServiceWatchdog.json and confirm with .\Invoke-WinServiceWatchdog.ps1 -ValidateConfig from the install folder (exit 0). No re-registration is needed; the next run picks the change up. A service removed from the list while unhealthy is logged once as event 1006 and forgotten. Delete ServiceWatchdog.state.json to reset the watchdog's memory (this may produce one fresh alert for a problem that is already known).

Useful commands on the server:

Get-WinEvent -FilterHashtable @{ LogName = 'Application'; ProviderName = 'ServiceWatchdog' } -MaxEvents 20
Get-Content "$env:ProgramData\ServiceWatchdog\Logs\ServiceWatchdog-$(Get-Date -Format yyyyMMdd).log" -Tail 50
Get-ScheduledTaskInfo -TaskName ServiceWatchdog

Checkup: has it restarted anything?

A successful restart is silent by default (no email), so this is the quickest way to see the watchdog doing its job. Event 1001 is written every time it starts a service:

Get-WinEvent -FilterHashtable @{ LogName = 'Application'; ProviderName = 'ServiceWatchdog'; Id = 1001 } -MaxEvents 25

Each entry names the service and the attempt it succeeded on. Use Id = 1002 for failed starts instead, or drop the Id filter for the last 25 events of any kind.

Testing an installation

Run from C:\ProgramData\ServiceWatchdog in an elevated PowerShell.

  1. .\Invoke-WinServiceWatchdog.ps1 -ValidateConfig -Verbosity High: exit 0 and a summary of the effective settings.
  2. .\Invoke-WinServiceWatchdog.ps1 -TestAlert: exit 0, a [TEST] email, event 1030.
  3. .\Invoke-WinServiceWatchdog.ps1 -DryRun -Verbosity High: every service listed with its status; nothing changed.
  4. Stop a non-critical listed service (Stop-Service Spooler) and run Start-ScheduledTask -TaskName ServiceWatchdog. Within a minute the service is running again and event 1001 is logged; no email unless NotifyOnRemediation is on.
  5. Disable a listed service (Set-Service Spooler -StartupType Disabled; Stop-Service Spooler) and start the task: an alert email names it as Disabled, events 1004 and 1010 are logged, the run exits 50. Restore it (Set-Service Spooler -StartupType Automatic) and start the task again for the recovered email and event 1005.
  6. .\Invoke-WinServiceWatchdog.ps1 -SendHeartbeat: event 1012 and a row for the host in the WatchdogHosts table (Storage browser in the Azure portal).
Seeing the Azure side

In Application Insights on the Function App: requests | where name == "SendServiceWatchdogAlert" lists every call with its status code, and traces | where message has "ServiceWatchdog" shows the function's own log lines including the run id and host name. Requests and exceptions are never sampled.

Secrets and rotation

Function key (the value in every server's ServiceWatchdog.json)

Keys are named and several can be valid at once, so rotation has no outage window.

  1. Create a new named key: re-run the install script with -FunctionKeyName watchdog-2027q1 (everything else is reused and the new key is printed once), or create it directly: 
    $site = (Get-AzWebApp -ResourceGroupName 'rg-servicewatchdog' -Name 'func-svcwatchdog-abc123').Id
$created = Invoke-AzRestMethod -Method PUT -Payload '{"properties":{"name":"watchdog-2027q1"}}' `
    -Path "$site/functions/SendServiceWatchdogAlert/keys/watchdog-2027q1?api-version=2024-04-01"
($created.Content | ConvertFrom-Json).properties.value   # the new key; paste it into the vault
  2. Update Webhook.FunctionKey on every server (RMM script or by hand) and verify each with .\Invoke-WinServiceWatchdog.ps1 -TestAlert (exit 0). Update [PASSWORD VAULT ENTRY].
  3. Delete the old key: Invoke-AzRestMethod -Method DELETE -Path "$site/functions/SendServiceWatchdogAlert/keys/watchdog?api-version=2024-04-01". Any server that was missed starts logging event 1013 and exit 10, which is the signal to fix it.
  4. If the rotation is because the key leaked, also review the WatchdogHosts table (Storage browser in the portal) and delete rows for host names that are not real servers; the README section "Recovering from a leaked function key" has the CLI commands. A real server writes its row again on its next heartbeat.

SMTP2GO API key (or SMTP password)

  1. In SMTP2GO create a new API key with the same scope (Emails only) and rate limit. Do not revoke the old one yet.
  2. Store it in Key Vault (Key Vault Secrets Officer on the vault is required; the deployer received it from the template): Set-AzKeyVaultSecret -VaultName 'kv-svcwatchdog-abc123' -Name 'Smtp2GoApiKey' -SecretValue (Read-Host -AsSecureString) (SmtpPassword for the SMTP provider).
  3. Make the app pick it up now rather than at the next 24-hour refresh: Restart-AzWebApp -ResourceGroupName 'rg-servicewatchdog' -Name 'func-svcwatchdog-abc123'.
  4. Verify with .\Invoke-WinServiceWatchdog.ps1 -TestAlert on any server; the [TEST] email proves the new key works end to end.
  5. Revoke the old key in SMTP2GO and add a change-log row below.

Runtime version check

Check before 10 November 2026

The Function App runs PowerShell 7.4, whose support on Azure Functions ends on 10 November 2026. PowerShell 7.6 is the successor and was in preview (Windows plans only) when this was written. Before that date:

  1. Read the current support table at https://learn.microsoft.com/azure/azure-functions/supported-languages.
  2. When 7.6 is generally available on Windows Consumption, re-run the install script with -PowerShellVersion 7.6 (or set the powerShellVersion template parameter). The function ships no modules, so the bump is a parameter change and nothing else.
  3. Run the install script with -SendTestEmail, then -TestAlert from one server, and add a change-log row.

Troubleshooting

SymptomLikely causeFix
Install script exits 50 at the publish step with a 401 from Publish-AzWebApp SCM basic authentication is disabled on the app or by Azure Policy Update Az to 9.7.1 or later, or allow basic auth on the SCM site (Invoke-AzRestMethod -Method PUT -Payload '{"properties":{"allow":true}}' -Path "$site/basicPublishingCredentialsPolicies/scm?api-version=2024-04-01") and re-run. A policy assignment may set it back.
Redeploy after deleting the resource group fails: a vault with the same name exists in a deleted state Purge protection reserves the Key Vault name for 90 days Recreate a resource group with the original name, run Undo-AzKeyVaultRemoval -VaultName ... -ResourceGroupName ... -Location ..., then re-run the install script; or use a different -BaseName or resource group name.
Redeploy after deleting only the Function App fails with RoleAssignmentUpdateNotPermitted The old role assignments for the deleted identity still exist under the same names In Access control (IAM) on the Key Vault and on the storage account, delete the assignments showing "Identity not found", then re-run.
-TestAlert works when run by hand but the scheduled task logs event 1011 (timeout) SYSTEM uses the machine-wide WinHTTP proxy, not the signed-in user's browser proxy netsh winhttp show proxy; set it with netsh winhttp set proxy proxy-server="proxy.example.com:8080" bypass-list="<local>" or netsh winhttp import proxy source=ie. Confirm outbound 443 to the Function App host name is allowed.
Event 1013 on every run 401: wrong or deleted function key. 403 with site_not_allowed: SiteName not in WATCHDOG_ALLOWED_SITES Paste the current key from [PASSWORD VAULT ENTRY]; or add the site to the allowlist.
Event 1014 on every run The function rejected the payload (the log line carries the function's error list); usually a server on a different worker version than the function Keep the endpoint scripts and the function on the same version.
Function answers 500 config_unresolved A Key Vault reference did not resolve: secret missing, the app's identity lacks Key Vault Secrets User, or the app has not restarted since the secret was created Re-run the install script (it seeds the secret) or Restart-AzWebApp. The portal's "Key Vault Application Settings Diagnostics" blade names the failing reference.
Alerts resume up to an hour late after a mail provider outage The per-host rate limit (6 per hour) counts attempts, and the server re-posts its pending event every 5 minutes Wait it out, or restart the Function App (the counter is in memory). A 429 naming the global limit (60 emails per hour across all servers) means the whole fleet sent that many emails in the hour; look at what is alerting.
Digest says "no hosts have ever reported" No server has reached the function yet On the servers: Get-ScheduledTaskInfo -TaskName ServiceWatchdog, the config, and events 1011/1013.
Digest lists a server as stale Its task is disabled, the server is off, or every delivery fails Check the task's last run result and the events above on that server.
Installer exits 1 at once with a message about elevation Not running as administrator Open PowerShell as administrator.
Installer exits 2: config outside the install folder -ConfigPath points outside -InstallPath, the only folder whose permissions are restricted Keep the config inside the install folder.
Worker warns that the event source is missing The worker was run by hand without elevation before the installer registered the source Run the installer, or run the worker elevated once; file logging continues regardless.

Removing the watchdog from a server

Elevated: .\Unregister-WinServiceWatchdogTask.ps1 removes the task and keeps the config for later re-registration; add -RemoveEventSource -RemoveFiles -Force for a complete unattended removal (the install folder, including the config with the key, is deleted). Service Control Manager failure actions set with -SetServiceRecovery are left in place. Then delete the host's row from the WatchdogHosts table so the digest stops listing it as stale.
